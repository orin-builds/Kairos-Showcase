# Kairos · 系统设计概览

## 为什么是多端系统

GPT 擅长理解、推理和解释，App 更适合承接设备上的持续交互与实际执行，服务器则负责受控连接与协议协调。Kairos 把这些职责组合为一个项目，而不是让聊天模型直接控制全部业务状态。

## 三条不能混淆的边界

### 1. 推理与事实

模型可以提出假设和计划，但事实必须有明确来源。用户的真实执行、记录的版本和已确认的变更，不能被对话中的推断替代。

当信息缺失时，系统应表达“未知”，而不是填入看似合理的完成状态、时长或能力判断。

### 2. 候选与提交

建议生成、预览、明确确认、系统提交、设备应用和实际执行是不同阶段。每一阶段都需要自己的条件和结果，不依赖一句“已完成”贯穿全链路。

计划相关的变更保留准备、预览、用户确认和提交的边界；角色、版本、范围与容量等检查应由确定性规则承担。

### 3. 协调与数据归属

服务器连接 App 与 GPT，但位于中间层不意味着拥有所有业务数据的无限写权限。各端仍需遵守既有数据归属、事务和授权边界。

App 的本地持久化、服务器的接口状态和 GPT 的会话上下文，不应被理解为一份天然一致的共享数据库。

## 从一次规划到下一轮调整

1. 用户提供目标和现实约束；系统按授权取得必要上下文。
2. GPT 总控与学科协作形成结构化候选，保留依据与不确定性。
3. 服务与业务规则检查候选，生成可理解的预览；需要写入时由用户明确确认。
4. App 承接适用的日常任务与操作，记录实际执行结果。
5. 各端通过授权同步和回执核对衔接结果，GPT 据此进行复盘与下一轮建议。

这是一条设计层面的逻辑流程，不表示每个步骤在所有版本或环境中均已启用。

## 为什么不把“打勾”当成“掌握”

执行反馈与学习证据回答不同问题：完成练习、答对题目、独立完成以及隔一段时间后仍能迁移运用，并不是同一件事。

Kairos 的工程与交互设计强调保留这些区别，防止“完成任务”在多端传递后被放大为没有依据的能力结论。
