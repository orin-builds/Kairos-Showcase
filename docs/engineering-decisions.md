# Kairos · 工程思路与取舍

## 用明确边界约束 AI，而不是只写提示词

自然语言约束不能代替业务授权。角色、范围、版本和确认条件应在实际接口与业务链路中校验，模型的职责是产生可讨论的候选与解释，而不是自行获取更大的写入权限。

## 复用业务系统，不再造一份事实

接入 GPT 时，容易出现第二套任务状态、另一套积分计算或只存在于聊天中的“事实”。Kairos 的方向是复用既有业务记录、规则与事务边界，把跨端能力作为适配和协调，而不是重建平行系统。

## 将成功拆成可核对的阶段

接口返回、候选被接受、设备成功应用和用户真正执行，不是同一个成功条件。明确阶段与回执，可以降低重复请求、晚到结果或中断恢复带来的误判。

## 本地体验与在线能力分层

App 面向日常任务与设备交互；Server 与 GPT 承接需要联网的协作。是否能在网络不可用时继续某项操作，应以具体实现为准，不把“本地优先”宣传成整个系统完全离线。

## 自动化验证与设备验收分开

领域模型、数据适配和接口协议可以通过自动化测试检查。应用守护、前台识别和设备交互还需要真实设备验证，不能用单元测试通过替代实际体验或系统行为的验收。

本展示仓库不引用没有可公开证据支撑的性能数字、通过率或用户效果。

## 展示与开发分开

公开展示仓库只从零编写经过筛选的文档，不从私有开发仓库复制 Git 历史。这样可以展示系统设计与工程思考，同时降低误带入凭据、截图、日志或个人数据的风险。

新增图片与演示前，应逐项检查账号、手机号、通知、时间地点、设备标识、服务器地址和真实学习记录，确认可公开后再加入。
