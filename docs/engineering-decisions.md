# Kairos · 工程案例与取舍

[项目首页](../README.md) · [系统架构](system-design.md) · [验证与状态](verification-and-status.md)

以下案例从本地工程、协议和测试资料中提炼，重点展示问题与选择，不复制私有实现。**“存在实现或测试”与“本轮已执行验证”分别对待**；本次公开文档整理没有运行生产或真机验收。

## 案例一：AI 说“改好了”，为什么系统还不能显示成功？

### 问题

生成计划、通过校验、提交请求、设备应用和实际执行，是不同的事件。把它们合并成一个成功标记，会造成任务没有变化但聊天已经承诺完成的情况。

### 选择

让候选先经过校验与预览，保留明确的用户确认。每个处理阶段都应有可核对的结果；结果未知时继续呈现未知，而不是猜测。

| 阶段 | 可以声称什么 | 不能声称什么 |
| --- | --- | --- |
| 候选生成 | 已形成一个建议。 | 已修改计划。 |
| 校验完成 | 在该校验范围内通过检查。 | 之后的数据不会变化。 |
| 用户确认 | 用户同意所见的变更。 | 所有端都已成功应用。 |
| 业务应用 | 对应业务边界完成了处理。 | 用户已实际完成任务。 |
| 执行反馈 | 收到对应的实际行动记录。 | 必然掌握了相关知识。 |

### 取舍与验证

显式阶段比一个“成功”按钮复杂，但能解释中断位置。验证要覆盖重复确认、候选失效、晚到回执和设备应用失败，而不仅是顺利的一次请求。

## 案例二：候选没变，但它依赖的时间已经变了

### 问题

假设 GPT 在“今晚有 70 分钟”的条件下生成候选。预览期间用户把可用时间改为 30 分钟。即使候选内容完全没变，它也可能已经不适用。

### 选择

上下文适配记录实际依赖的目标、材料、可用时间与执行对象及其版本，在确认边界重新核对。受影响的依赖变化时，回到规划或确认流程。

没有依据的材料范围不能随便补齐；学科提供的最小、标准、扩展范围是替代选项，不能将三档相加来证明“安排得更完整”。

### 取舍与验证

乐观版本检查可能要求用户重新确认，但比静默执行过期计划更可解释。测试应分别改变相关与无关对象，检查是否发生正确的失效，而不是任何更新都使所有候选失效。

## 案例三：部分完成后补完，怎样避免重复奖励？

### 问题

一个任务可能经历“完成大部分 → 补充完成 → 网络重试 → 再次收到相同回执”。如果每次都按全量重新结算，就可能重复获得奖励；如果所有后续提交都一律丢弃，又会漏掉合法的增量。

### 选择

复用既有任务与结算业务模型，区分重复请求与新的有效状态变化。现有整合资料描述了精确重放不重复生效、合法升级按新增差额处理的原则；学习更正不随意重写历史经济账。

用于解释的逻辑是：

```text
同一个有效操作重复送达 → 核对已处理结果，不再次产生副作用
合法的新状态变化       → 通过既有规则计算本次允许的变化
仅更正学习描述         → 不自动重放历史奖励
```

这是公开概念说明，不是实际奖励公式或可调用接口。

### 取舍与验证

保留事件身份和历史处理结果需要额外状态，但单纯在 UI 禁止连点不够。验证应覆盖相同请求、乱序请求、部分到全部、相同标识不同内容，以及业务失败后的恢复。

## 案例四：为什么“完成”不能直接变成“掌握”？

### 问题

学习任务完成可能意味着“读完了”“照着讲解做完了”或“独立做对了”。将这些情况压成一个标签，会让下一轮规划跳过用户仍然不确定的内容。

### 选择

保留执行程度、正确性、帮助程度、实际范围与来源等不同维度。现有学习模型测试明确区分未知、受阻、未执行、部分完成与完成；模型和角色契约禁止靠猜测补全缺失事实。

| 演示反馈 | 可以保留的事实 | 不该自动得出的结论 |
| --- | --- | --- |
| “做完了，尚未核对答案。” | 用户报告完成；正确性未知。 | 全部正确。 |
| “大部分会做，后面看了讲解。” | 部分完成；至少部分借助帮助。 | 独立完成并掌握。 |
| “今天没有发反馈。” | 当前未收到对应记录。 | 今天没有学习。 |

### 取舍与验证

数据语义更细，不代表让用户填写复杂表格；交互应支持逐步补充。重点验证状态投影、未知值保留、来源修订和聊天复述去重。

## 案例五：功能不断加，历史数据不能被“重新初始化”

### 问题

长期使用的 App 会经历多次 Schema 演进，还可能整合来自不同分支的结构。应用能启动并不证明历史任务、积分和关联关系都保留了。

### 选择

通过增量迁移延续既有持久化结构。当前本地迁移测试包含多种历史结构与连续版本路径，关注旧记录、经济状态、学习字段和关联是否保留。

新增结构也不应凭空赋予用户旧数据中不存在的新事实：例如新增学习字段不能让历史任务自动变成“已掌握”，新增状态表不能默认为发生过一次真实执行。

### 取舍与验证

迁移测试比清空重建更费工，但它保护的是用户积累的记录。主机测试可以检查数据结构和转换；真实设备数据库升级与异常中断还需要独立验收。

## 案例六：应用守护不能只展示一个“已开启”开关

### 问题

用户看到“已开启”时，可能自然理解为保护正在有效执行。但系统权限、服务绑定、前台识别和设备差异都可能使这种推断不成立。

### 选择

将配置状态与实际工作状态分开考虑，为异常提供可理解的状态和恢复路径。保持用户控制，不以隐藏操作或扩大权限掩盖失效。

### 取舍与验证

设备限制无法靠一组领域单元测试完全证明。需要在受支持的真实设备上检查前后台切换、权限变更、服务中断与恢复；因此公开材料不作“绝对拦截”或“零曝光”承诺。

## 跨案例的共同原则

1. **规则有明确归属**：GPT 产生候选，确定性业务规则决定能否应用。
2. **成功必须有范围**：某个模块成功不代表全链路成功。
3. **未知有价值**：保留未知通常比产生一条错误事实更安全。
4. **恢复也要设计**：重复、中断和迁移是正常工程工作的一部分。
5. **展示尊重证据**：不用历史测试数量、合成数据或概念流程冒充当前生产能力。

这些选择可能增加开发和交互成本，但能让系统状态更容易理解、核对与持续演进。
